Executive summary

We propose a bounded, behavior-preserving refactor of TensileLite that turns feature additions from multi-file, cross-language edits into single-file extensions — and unlocks runtime kernel generation, which is what makes the shipped library small. The work is grounded in the current source, sequenced to carry zero performance or behavior regression, and honest about what it has not yet proven.

TensileLite is the Python code generator inside hipBLASLt that emits GPU assembly for matrix-multiply (GEMM) kernels. [Verified: projects/hipblaslt/tensilelite/CLAUDE.md.] It works, and it is fast. The problem is not correctness; it is cost of change.

The problem, in three numbers

  • Two files hold most of the logic and most of the risk: KernelWriter.py (11,086

lines) and KernelWriterAssembly.py (19,896 lines) — 30,982 lines across two files that no one person fully understands. [Verified: EXPANSION-v5.md A.1.]

  • Adding any new operation is closed off by construction: the operation

dispatcher handles "GEMM" and then raises on everything else. [Verified: Problem.py:944-948.]

  • The kernel is emitted as one fixed procedure — one prologue, one main loop, one

epilogue — with no way to compose two matmuls or carry a running reduction across the loop. [Verified: KernelWriter.py:5351.] That single fact forecloses fused attention.

What we propose

One serializable, versioned CodegenRequest descriptor replacing the live in-process objects that cross into codegen today; an open registry replacing the closed if == "GEMM" dispatch (and the parallel data-type elif chains); and a composable kernel model replacing the fixed procedure. Everything resolves through one descriptor — not two parallel registries.

The payoff, made concrete

Adding a Mixture-of-Experts scheduling variant today is a change across ~8 files in three layers — Python codegen, Python serialization, and the C++ runtime — whose most likely failure is a silent wrong result when the layers drift. After the refactor it is one new ~12-line file, selected by one versioned key, unit-testable in five lines without a GPU. [Worked in full in the MoE example.] The same shape holds for attention (a new operation class: two new files, zero edits to the GEMM path) and for runtime JIT (generate on demand instead of shipping pre-tuned objects).

The cost and the risks — stated plainly

This is a proposal. No code was changed, no tests written, no commits made. The central structural move (the composable kernel model) is the highest-risk change, and we have not yet proven that a single GEMM stays byte-identical under it — that must be retired empirically before anything is locked. Of the nine governance requirements, only one is fully met today; seven are partial (they specify CI gates and counters that must still be built) and one is an open conflict (there is no experimental wall yet, and ExperimentalLibrary already couples into production driver code). The scorecard states all of this without softening.

What we need to proceed

Approval to build "step 0" first: an all-arch byte-identical assembly CI gate and a throwaway fused-attention prototype as a forcing function. Those two retire the biggest unknowns before any boundary is moved.

Terms used in this document

Only the project-specific ones; the committee knows the rest.

  • GEMM — general matrix multiply, C = A·B; the compute primitive the library

is built around.

  • Codegen — Python that emits GPU assembly source from a problem description,

because the valid (arch, dtype, tile, schedule) space is tens of thousands of variants.

  • God-file — one source file grown to own many unrelated responsibilities;

editing it risks unrelated behavior inches away.

  • Seam — a point where one behavior can be replaced or tested in isolation

(Feathers 2004). Creating seams where none exist is the point of this refactor.

  • Byte-identical — the generated assembly matches the current output bit for

bit; the proof that a refactor step changed no behavior.

The problem: cost of change, not correctness

TensileLite works and is fast. What it lacks is any cheap way to change it. Four structural facts — two god-files, a closed operation registry, a fixed kernel skeleton, and a live-object build boundary — make every extension a high-risk edit, and together they form a local equilibrium where each problem makes the others harder to fix. This section establishes each on measured ground.

The two god-files concentrate the risk

FileLines of codeMethodsself. accesses
KernelWriterAssembly.py19,8963323,597
KernelWriter.py11,0862023,081
Bottom line. Just over 30,000 lines in two files, 534 methods, and 6,678 places where a method reaches into shared object state. Each of those accesses is a hidden dependency between methods that may sit thousands of lines apart. To change one method safely you must know which of the other 533 touch the same field — a question you cannot answer by reading a 30,000-line file in reasonable time. The practical result: engineers add behavior by adding conditions inside existing methods, which grows the file and makes the next change harder. That is not a character flaw; it is the natural outcome of a file with no seams. [Verified: line and method counts from the two files on the current tree.]

Adding an operation is closed off by construction

When TensileLite builds a problem description, Problem.__init__ reaches this gate.

Tensile/SolutionStructs/Problem.py:944-948:

if self["OperationType"] == "GEMM":
    self._checkIfSupportedGEMMType()
    self.initGEMM()
else:
    raise Exception("Unsupported OperationType = %s" % self["OperationType"])

"GEMM" is the only valid value; the else raises immediately. A parallel numeric form at Problem.py:1108 (isGEMM() returns self.operationType == 0) confirms the same thing from the other side: TensileLite knows exactly one operation.

Bottom line. Adding Attention, Convolution, or a fused softmax-GEMM is not a new-file-and-register operation — it requires editing this gate, in the god-file, without breaking the working path. The dispatch encodes every valid choice directly in source instead of reading them from a registry (a lookup table from name to handler, where a new entry changes no existing code). The registry is the fix; it does not exist today. [Verified: Problem.py:944-948, Problem.py:1108.]

The kernel body is a fixed procedure, not a composable structure

Every kernel follows a rigid skeleton. The entry point is kernelBody at KernelWriter.py:5351, which calls its phases in a fixed order:

PhaseLine
preLoop5381
setupNewTile2652
openLoop10226
noLoadLoop (main loop)4020
closeLoop10233
postLoop5168
Bottom line. One prologue, one main loop, one epilogue — always. There is no mechanism to compose two matmuls in one kernel, and none to carry a running reduction across a loop that spans two operations. Fused attention needs exactly that: a GEMM for scores, a softmax reduction over them, and a second GEMM for the weighted sum, all on-chip to save bandwidth. That is not a configuration of the existing skeleton; it is surgery on kernelBody. Bandwidth-optimal attention is structurally impossible under the current loop model. [Verified: KernelWriter.py:5351 and the phase line numbers in current source.]

The build boundary carries a live object, so runtime JIT is impossible

TensileLite runs in two phases: an offline build that reads YAML, generates kernels, and writes a library; and runtime, where an application loads that library and picks a kernel. The handoff between them should be a clean, versioned, serializable representation. It is not.

What crosses the boundary is a live Solution — a Python dict mutated by a chain of normalize-and-derive calls — passed straight into the emitter _getKernelSource at KernelWriter.py:10750:

def _getKernelSource(self, kernel: Solution):

It is never serialized. It is built by a KernelWriterAssembly instance at TensileCreateLibrary/Run.py:1078, which reads the process-global singleton Common/GlobalParameters.py at emit time.

Bottom line. Three things that should be independent are fused: authoring-time spec and emit-time derived state live in the same dict with no checkpoint between them; the emitter reads process globals that are recorded nowhere, so any other caller must replicate that exact global state or silently get different output; and because the contract is a live Python object, it cannot cross a process, a network, or a disk cache. Runtime JIT — an application requesting a specialized kernel on demand — needs all three of those. Under today's design JIT would mean duplicating the entire offline pipeline inside the user's application. The same fact drives library size: unable to specialize at runtime, TensileLite must precompile every kernel it might ever need. [Verified: KernelWriter.py:10750, TensileCreateLibrary/Run.py:1078, Common/GlobalParameters.py import.]

Why this is one problem, not four

The god-files exist because every extension goes into them — and it goes into them because the OperationType gate is not a registry, the loop skeleton is hardcoded in kernelBody, and no serializable boundary defines what the emitter actually needs. The closed gate persists because threading a new type through the god-files is so large that no one takes it on. A serializable boundary is blocked because defining one requires a clean interface the god-file does not have — any attempt is either incomplete (missing one of 6,678 self. reads) or replicates the whole state. Each problem makes the others harder to fix. The exit is a single move: introduce a typed, serializable seam between what the emitter needs and how it produces it. That seam is what the rest of this proposal builds.

What the numbers mean for risk

Three concrete consequences follow from the structure above.

Risk 1: invisible side effects from self-access density. A field read 3,597 times across 19,896 lines is a field where renaming it, type-changing it, or adding a condition around it can break behavior at dozens of sites that are not near the edit. Enumeration by inspection is not feasible.

Risk 2: regression catchment gaps from indirect-only coverage. A change to GlobalWriteBatch.py that breaks an uncovered configuration will pass the full test suite and ship. The breakage appears in production or in a downstream CI job running a broader configuration set.

Risk 3: slow debugging from lack of isolating tests. A failing golden says the assembly changed. It does not say which function or file caused it. Finding the cause requires tracing a pipeline that spans KernelWriter.py (11,086 lines), KernelWriterAssembly.py (19,896 lines), and GlobalWriteBatch.py (3,194 lines). With isolating tests, a failing test names the file and the behavior.

What the golden harness does protect

The characterization harness is the primary safety net for any structural refactoring. It provides:

  • A CPU-only, no-GPU smoke test for assembly correctness on 98 known-good configurations.
  • A byte-level diff signal: any change to emitted assembly -- register renaming, instruction reordering, operand changes -- fails the corresponding golden.
  • Per-architecture attribution: the gfx90a, gfx942, and gfx950 JSON files allow targeting the golden suite at a specific GPU family.

The Tensile/verify_stinky_comment_vs_elf_text.py script provides a second layer: ELF-level verification that emitted text matches what the assembler produces in binary form. Source: file exists at the listed path (Verified).

Bottom line. Run the 98 goldens before and after any seam move. Pass before and after means no covered configuration regressed -- necessary, not sufficient. It does not protect uncovered configurations, and it does not protect AsmStoreState.py behavior the covered configurations do not exercise. We propose adding isolating tests for the three high-state files before moving any seam in those files.

The plan: seams and the graded backlog

We have enumerated 15 actionable refactor seams across TensileLite, graded each against a structural completeness gate, and ranked them by leverage. This section presents the backlog and the evidence behind it.

A seam (Feathers 2004) is a point where one behavior can be replaced or tested in isolation, without touching the code around it. TensileLite has very few seams today, which is why testing a scheduling behavior requires a full GPU run instead of five lines of Python. Creating seams is the work; this backlog identifies where to cut first.

How the seams were found

Two tools were run across the Tensile/ package. Neither is sufficient alone.

Tool 1: deterministic import-graph scan. Static analysis of every Python import built a directed graph of module dependencies. The scan looked for two signals:

  • Coarse coupling seams — groups of modules heavily coupled to each other but not to the rest of the codebase. Each is a candidate for isolation.
  • Cycles — loops in the import graph (A imports B, B imports C, C imports A). A cycle blocks testing: you cannot import any module inside the loop without loading the entire ring.

Result: 15 coupling/cycle seams identified. [Verified: work-v5/seams.json, work-v5/enumerate.py]

Several of those 15 were test-coupling noise — they appeared because test files imported production modules in unusual patterns, not because production code was entangled. Human judgment is required to separate real seams from false positives.

The import graph cannot see inside a single large file. If KernelWriterAssembly.py holds five unrelated responsibilities but imports no outside module that exposes the split, the graph shows one node with many edges — not five opportunities.

Tool 2: size and cohesion scan for god-objects. This measured lines of code, method count, and self-access count for the largest classes. Self-access count — the number of times a method reads or writes self.something — surfaces hidden internal state that nothing outside can see and that the import graph therefore cannot find. This scan identifies where a cut is needed; it does not identify exactly where to cut. That requires reading the code.

Combined result: 15 refactor seams, each ranked by leverage. A sixteenth seam (t2-asmstorestate, targeting Tensile/AsmStoreState.py) is planned test-first: the module has zero characterization tests, which blocks starting implementation but not authoring a plan. Its full contract and decomposition are in Appendix A, with a step-zero golden-test harness as the first removal gate. [Verified: work-v5/backlog-v5.json; plan work-v5/t2-asmstorestate/plan/plan-index.authored.json]

One epic (sparse-mx) spans 723 sites across KernelWriterAssembly.py and KernelWriter.py. An epic is too large to be a single seam; it is a sequence of seams that must be executed in order after the smaller seams reduce the blast radius. [Verified: work-v5/backlog-v5.json]

Top seams by leverage

Leverage here means: fixing this seam unblocks or de-risks the most other work.

Rank 1: t2-kwa (KernelWriterAssembly.py, 19,896 LOC, 332 methods, 3,597 self accesses)

Every new kernel feature — new scheduling mode, new operation type, JIT compilation — requires an edit inside it. Because all behavior is fused together, a careless edit can perturb unrelated GEMM output. The plan extracts one cohesive responsibility behind a value or state object. After this seam exists, adding a scheduling variant no longer requires editing a 20,000-line file. [Verified: work-v5/backlog-v5.json rank 1]

Extracting that state into an injected value object creates a seam between "what state are we tracking" and "how do we emit assembly for it." Rank 3: t1-scc-cycle (import cycle across 7 modules)

Solution.py is the configuration object that drives all of codegen. It validates parameters, resolves derived values, and serializes to MsgPack format (compact binary encoding used to ship the solution to the C++ runtime). With 13 test bindings already mapped, this seam has the best test coverage of the top four. Extracting a first responsibility makes it possible to test solution construction without standing up the entire codegen pipeline. [Verified: work-v5/backlog-v5.json rank 4]

Scope: first slices, not full decompositions

Each plan in the backlog targets a first responsibility — one cohesive thing to extract from the god-object. It does not fully decompose the god-object in a single step. That is by design.

Full decomposition of a god-object with 332 methods is months of work per object. The first-slice approach extracts the one responsibility most likely to be tested and stabilized, proves the shim pattern works without breaking existing tests, and leaves the god-object smaller but still present for subsequent iterations. Each slice reduces the blast radius of the next.

Implementation protocol

For each seam:

  1. Read the plan document at the path listed in backlog-v5.json under plan_md. Confirm the current surface matches what the plan documents before making any changes — the codebase evolves.
  2. Implement the compatibility shim first. The shim lets old callers keep working while the new interface is built beside them.
  3. Run the test bindings listed in the plan before and after. Stop and diagnose before continuing if any binding breaks.
  4. Do not remove the shim until the removal gate condition stated in the plan is met.

For reviewers: a PASS grade means the plan is structurally complete. The reviewer's job is to evaluate whether the implementation matches the plan's current surface, target surface, and shim contract. The PASS grade is not the approval. The reviewer is.

The target architecture

Three structural changes eliminate the four problems in Part 1: a versioned serializable descriptor replaces the live Solution at the codegen boundary; an open registry replaces two closed dispatchers; and a composable kernel model replaces the fixed procedure. Every change flows through one mechanism -- the descriptor -- not parallel tables that drift.

The problem the architecture solves

The three pieces of the target architecture

Piece 1: the versioned serializable descriptor (CodegenRequest / CodegenResult)

Piece 3: the composable kernel model

The current kernelBody (KernelWriter.py:5351) is a fixed chain -- preloop, one mainloop, epilogue -- with no mechanism to carry a running reduction into a second loop. That is why SoftmaxGenerator.py is a standalone top-to-bottom generator with its own argument and meta models: there was no other way to add a multi-phase kernel. The composable kernel model introduces named slots and first-class reductions:

# Tensile/Codegen/model.py  (new file -- proposed)  [J]
class KernelModel:
    def __init__(self):
        self.stages = []         # ordered fragments: preloop / mainloop / epilogue
        self._reductions = []    # first-class state carried ACROSS the loop
    def add_matmul(self, lhs, rhs, *, transpose_rhs=False, feeds=None):
        h = MatmulStage(lhs, rhs, transpose_rhs, feeds)
        self.stages.append(h); return h
    def carry_reduction(self, reduction):
        self._reductions.append(reduction); return reduction
    def lower(self, emitter):    # composes stages -> rocisa Module
        module = emitter.new_module()
        for st in self.stages:
            st.emit(emitter, module, self._reductions)
        return module
Bottom line. add_matmul adds one matrix-multiply stage. carry_reduction registers a running value -- a running maximum or sum for online softmax -- that the model passes to every following stage. A single GEMM is one add_matmul call. Fused attention is two calls with a carry_reduction between them. The model does not inspect the operation type; the compose callable in OperationSpec does.

KernelModel.lower(emitter) is also the intended attach point for a lower serialization seam. It is the scheduler-output-to-emitter step, so if the stage representation gains a plain-data projection (to_schedule()/from_schedule()), a serializable program schedule falls out of this layer rather than requiring a new one -- see Worked example: Runtime JIT. That seam is PLANNED and gated on lifting register allocation out of emission; the architecture is shaped to host it, not to require it.

What Fused Attention is and why it cannot be a GEMM variant

Transformer models compute attention as:

Scores  = Q * K^T          (first matrix multiply)
Weights = softmax(Scores)  (row-wise normalization)
Output  = Weights * V      (second matrix multiply)

The naive implementation launches three GPU kernels and writes the Scores matrix -- up to 4 million float values per batch item for a 2048-token sequence -- to GPU global memory between steps. Fused Attention avoids that write by merging all three steps into one kernel body, keeping Scores in GPU registers (private to each wave) throughout.

The structural difference that makes this non-trivial is the online softmax reduction (Milakov & Gimelshein 2018): the loop iterates over K and V tiles, accumulating partial scores while carrying a running maximum and running sum. After the loop, it divides the accumulated output by the final running sum. That carried state -- the running max and running sum -- must be updated on every iteration and then applied as a final correction. It is not a scalar side effect; it rescales the accumulated output register tile on each iteration.

A plain GEMM is the degenerate case of this graph: one matmul node, no carried reduction. You cannot configure a GEMM kernel to carry a reduction across a second matmul. The loop structure itself must differ. That is why Attention is a new operation class, not a new GEMM variant.

The structural blocking constraint: KernelWriter.py:5351

kernelBody emits a fixed loop: for each output tile, multiply, accumulate, write. One reduction accumulator: the output tile itself.

Fused Attention requires the loop body to do additional work on each iteration:

  1. Compute the max of the current score tile.
  2. Compare it to the running maximum carried from previous tiles.
  3. Scale the previously accumulated output by exp(old_max - new_max).
  4. Update the running sum.
  5. After the loop, divide the accumulated output by the final running sum.

Steps 3 and 5 reach back into the accumulated output register tile and rescale it. There is no way to attach this behavior to the existing kernel body as a parameter or flag -- the loop structure must differ. The current kernelBody has no mechanism to carry state of this kind across iterations and apply a final correction. [Verified: KernelWriter.py:5351 and phase line numbers in current source.]

Adding Attention does not require editing any of the 10 == "GEMM" branches, because those branches now read "if no specific composer registered, treat as GEMM" rather than "if not GEMM, reject." GEMM itself is the degenerate case: add_matmul(A, B) with no carry_reduction node. All existing GEMM golden files remain byte-identical.

Why the three dangers go away

  1. Central registration, not 10 guarded branches. register_operation is a

single lookup. An unrecognized key raises at registration time with a clear error, not silently at runtime with a wrong result.

  1. Shared composition model. add_matmul and carry_reduction are defined

once. All operation types use the same graph primitives. The Attention composer does not need its own KernelArgument or KernelMeta dataclasses -- the framework derives the argument layout from the graph structure.

  1. Zero C++ edits for a new composer. The C++ runtime dispatches on the

operation key, not a C++-level enum of known operations. Adding a new key in Python does not require a C++ rebuild. (If the new operation requires a new C++-level launch strategy the runtime has never seen, that is a separate C++ change -- scoped to the launch strategy, not the operation type enum.)

  1. No god-file edits. The Attention composer does not touch KernelWriter.py.

The existing GEMM codegen path cannot be perturbed.

The acceptance test: byte-identical GEMM output

The single clearest proof that the refactor succeeded is running the existing GEMM test suite and confirming byte-identical output before and after. Because GEMM is the one-node degenerate case of add_matmul, the same codepath runs for all existing GEMM problems. Any golden file change means the refactor touched GEMM logic it should not have.

Worked example: Runtime JIT (generate kernels on demand)

The reason TensileLite ships a large pre-compiled library instead of generating kernels on demand is a single structural fact: the codegen entry point takes a live Python object that cannot be serialized. Fixing that fact -- replacing the live object with a typed, versioned CodegenRequest -- makes runtime JIT possible and reduces what ships to users. This section makes the case: what the current boundary costs, what the proposed boundary looks like, and what remains unproven.

The problem

TensileLite pre-compiles every kernel it might ever need. For six architectures and hundreds of problem sizes, the device library directory holds thousands of .hsaco files. Runtime JIT -- compile only the kernel the user actually needs, at call time -- is the alternative. It is how PyTorch's Triton backend and most shader compilers work. The first call pays a one-time compilation cost; the shipped library is small.

TensileLite cannot do this today, and the reason is not performance. It is architecture.

POST-REFACTOR: one request, shared offline and runtime

We propose a CodegenRequest -- a serializable, versioned record carrying only the typed facts that code generation needs. The offline path constructs it from a Solution. The runtime path constructs it from runtime facts. Both call the same lower_request function. No live Solution, no process globals, no KernelWriterAssembly at runtime.

The request type

# Tensile/Codegen/request.py   (NEW)
from dataclasses import dataclass
from typing import Mapping, Tuple, Union
JsonScalar = Union[int, float, str, bool]

@dataclass(frozen=True)
class Operand:
    role: str                          # "A", "B", "C", "D" for GEMM
    dtype: str
    layout: str
    index_assignments: Tuple[int, ...]

@dataclass(frozen=True)

    op_type: str                       # a key registered in the operation registry
    operands: Tuple[Operand, ...]
    produces: Tuple[str, ...]
    consumes: Tuple[str, ...]
    attrs: Mapping[str, JsonScalar]    # only typed facts; no live objects

@dataclass(frozen=True)
class CodegenRequest:
    schema_version: str                # "codegen.v1"
    arch: str
    op_graph: Tuple[OpNode, ...]
    tuning: Mapping[str, JsonScalar]   # only typed facts the lowering needs

Source: CODE-EXHIBITS-v5.md section 0. [Verified as the proposal; file does not yet exist in the codebase.]

Bottom line. Every field is a plain Python value -- string, integer, float, or tuple of those. No functions, no pointers, no process-global references. The request can be serialized to msgpack, sent over a socket, written to disk, or reconstructed from runtime facts. The schema_version field makes version mismatches detectable before data is misread.

How the schema eliminates silent divergence

The current system's silent-divergence risk -- Python writes a field, C++ does not learn about it, wrong result at runtime -- is addressed by making the request versioned and shared. The schema_version field is checked when a result is loaded. A mismatch is a loud, immediate error, not a silent mapOptional read. An unknown operation type key is a KeyError from the registry, not a silent default.

This does not eliminate versioning problems. It makes them detectable.

The rules we work under

Nine non-negotiable constraints govern every pull request that touches the seam. Violating any one of them is a rejection. This section states each constraint, its enforcement mechanism, and the honest gap between what is specified and what is machine-checked today.

The gap is large. As of 2026-07-16, no constraint is fully met; eight are enforced by review policy only; one is an open conflict. Step 0 closes the gap before any seam work begins.

The 9 constraints

1. Byte-identical assembly

After any structural refactor, the assembly text emitted by the GEMM path must match the pre-refactor output bit-for-bit for the same inputs. "Assembly text" is the full string returned by KernelWriterAssembly.getSourceFileString. One extra space, one reordered instruction, one changed comment: all fail.

The constraint exists because instruction-level ordering affects GPU performance. A semantically equivalent but differently ordered sequence can change benchmark results. "Correct and different" is not acceptable.

How the plan meets it -- with a correction. The characterization harness at Tensile/Tests/unit/characterization/_codegen/codegen_harness.py drives the full emit pipeline without GPU hardware, and 98 .ambr goldens exist across gfx90a, gfx942, and gfx950. But those goldens do not pin assembly text. matrix.py:32 digests_for_dir records only {basename, err} per kernel -- the parameter-hash kernel name and the emit return code -- and test_harness_smoke.py:76-79 states plainly that "the full assembly text is not hashed (it is order-coupled via the emitter's process-global MMA scheduler)." The emitted src is only sanity-checked (.amdgcn_target present, more than 1000 lines), never pinned. [Verified: matrix.py:32-55; test_harness_smoke.py:10-13,76-79; __snapshots__/test_emit_gfx942_char.ambr holds {file, kernels:[{basename, err}]} and no assembly.]

What is not yet built. The byte-identical gate has no substrate -- not merely no CI wiring. Two things are missing: (1) an order-stable, canonicalized full-text (or text-hash) golden for the codegen surface, blocked today by the process-global rocisa MMA-scheduler order-coupling that made the authors deliberately punt; and (2) the CI rule that a pull request may not update goldens and restructure code in the same commit. 2. The ratchet: characterize, change, unit-test, prove-equivalent, remove

3. One risk per pull request under a machine-checked semantic-LOC ceiling

Each pull request introduces exactly one structural change. A structural change is a change to the shape of the code -- a new abstraction, a moved boundary, a deleted coupling -- not a bug fix. The size is bounded by a machine-checked ceiling on semantic LOC (logic lines, excluding blank lines and docstrings). The ceiling number is set at step 0.

Large pull requests are opaque. Reviewers fall back to trusting the author. Small, focused pull requests make the reviewer's job mechanical: "did this one change preserve the goldens?" There is a second, external reason for small steps: NPI branches consume commits from public develop at a cadence and must not be overwhelmed by large, entangled changes. Each structural step must be independently shippable so it can be absorbed downstream one at a time.

How the plan meets it. The four steps in work-v5/feat-jit/brief.md section 3 produce four separate pull requests: CodegenRequest plus parity test; global reads moved to LoweringHints; offline smoke test; Attention stub. No pull request adds a new backend, moves globals, and removes the old path simultaneously.

What is not yet built. The CI job that counts semantic LOC in the diff and fails above the threshold does not exist. The ceiling is review policy until step 0 builds the check.

5. The serializable versioned request boundary

The object that crosses the boundary between "plan what to emit" and "emit it" -- the CodegenRequest -- must be serializable to a stable format with an explicit version field. Serializable means you can write it to disk and reconstruct an identical object from that file. Versioned means old files remain readable via a migration shim; new code rejects files from incompatible future versions.

Without this property, the offline JIT path is not reproducible. A CI failure cannot be replayed without saving the exact request that caused it. Schema drift between code versions makes saved requests unreadable.

How the plan meets it. Decision D-1 in work-v5/feat-jit/brief.md section 5 names this as open: semver with a monotone integer version field is the recommendation. Acceptance criterion AC-6 requires that a CodegenRequest serialized to JSON and deserialized produces a byte-identical CodegenResult on re-emit. [Verified: work-v5/feat-jit/brief.md sections 4 (AC-6) and 5 (D-1).]

What is not yet built. CodegenRequest does not exist. The JSON schema does not exist. The version field and migration shim do not exist. All are step-1 deliverables.

6. Maintenance must go down: the dual-path census

When old and new code paths run in parallel during migration, the count of call sites still on the old path must decrease with each pull request. The plan requires a machine-readable census script tracking three numbers per architecture:

  • converge-in N: pull requests before a given arch moves fully to the new path.
  • converge-out M: pull requests before the old path can be deleted for that arch.
  • per-arch fallback counts: for each GPU architecture (gfx90a, gfx942, gfx950, gfx1100, gfx1201, etc.), kernels still on the old path.

If the census shows new-path adoption is not monotonically increasing, the pull request is blocked.

Parallel paths are maintenance debt. Every bug fix must be applied to both paths. Every test must cover both paths. A stalled migration doubles maintenance cost indefinitely.

How the plan meets it. The attribution JSON files at Tensile/Tests/unit/characterization/_codegen/attribution-gfx90a.json, attribution-gfx942.json, and attribution-gfx950.json are the foundation for per-arch counting. [Verified: work-v5/feat-jit/brief.md section 1.6.]

What is not yet built. The census script does not exist. Converge-in and converge-out targets have not been set. The CI gate that blocks a pull request when the census trends upward does not exist.

7. The transition-maintenance lane

During migration, two engineers own two distinct responsibilities. The refactor owner advances the new path. The transition-maintenance owner keeps the old path working for production users. These are separate named roles. The lane has three sub-rules:

  • Every bug fix to the old path pins a characterization test first. The test comes before the fix and demonstrates the bug.
  • The god-file touch rate -- pull requests per week that require editing KernelWriter.py -- must trend downward. A flat or rising rate means the refactor is not reducing coupling as planned.
  • Bugs during the transition are routed to the old path unless the new path can handle them. The maintenance owner decides, not the refactor owner.

Without a dedicated maintenance lane, production stability degrades during migration. Engineers feel pressure to pause the refactor to fix bugs, stalling the migration. Separating the roles makes both responsibilities explicit and schedulable.

How the plan meets it. The plan names this as required organizational structure. The characterization test suite is the tooling the maintenance owner uses: a new failing test pinned to the bug is the entry condition for any bug fix.

8. The machine-checked wall: production vs. experimental code

Without this wall, a stub backend that raises NotImplementedError is one import path away from crashing a production workload on a routing bug or misconfiguration. Manual review of import graphs at every pull request is unreliable.

How the plan meets it. Acceptance criterion AC-5 in work-v5/feat-jit/brief.md section 4 states: "python -c 'import Tensile.KernelWriter' must not import any attention or multi-op module. The ask

The design is sound and honestly specified. The immediate work is building enforcement infrastructure, starting with the gates that retire the largest unknowns:

  1. An all-arch byte-identical assembly CI gate (Requirement 1) -- the empirical proof that refactor steps change no behavior. This first requires building a byte-level golden (the current goldens pin only kernel identity + emit code), which means taming the emitter's process-global scheduler order-coupling.

Those two deliverables convert the highest-risk unknowns from assumptions into measurements. Everything else is sequenced behind them.

What to do first (step 0)

The composable kernel model is the highest-risk claim in this project, and it must be retired empirically before any other boundary is moved. Two facts drive this sequencing: (1) we have not yet proven that a single GEMM built through composition produces byte-identical assembly to the existing monolithic path; (2) Fused Attention's cross-loop softmax reduction has not been shown to fit the composed structure. Building the registry, the CodegenRequest boundary, and the MoE strategy on top of an unverified composable model means unwinding all of that work if the model fails. The seven steps below are ordered to retire the highest-risk claim first, then build everything else on the proven foundation.

The seven steps, in order

Each step has a machine-checkable done condition. A step is not done until its done condition is satisfied. Starting the next step early defeats the purpose of the ordering.

Step 1. Build a byte-level golden, then the all-arch byte-identical assembly CI gate

The emit harness already exists at Tensile/Tests/unit/characterization/_codegen/codegen_harness.py, and 98 .ambr goldens plus per-arch attribution JSONs sit beside it. But the goldens pin {basename, err} -- kernel identity and emit return code -- not assembly text; the full text is deliberately not hashed because emit is order-coupled through the emitter's process-global MMA scheduler. [Verified: matrix.py:32-55; test_harness_smoke.py:76-79.] So this step has two parts, not one:

  1. Make the golden pin bytes. Tame the process-global scheduler order-coupling so two emits of the same kernel are text-stable, then add an order-stable canonicalized full-text (or text-hash) golden. canonicalize_asm already normalizes random label suffixes; it must be extended to a stable full-text digest. verify_stinky_comment_vs_elf_text.py provides ELF-level diff verification as a cross-check. [Verified: codegen_harness.py:58-78.]
  2. Wire it into CI across gfx90a, gfx942, and gfx950 and block merge on any assembly change.

Done condition. CI blocks merge on any PR that changes canonicalized assembly text for any pinned kernel on any of the three architectures. A file-addition commit does not break the gate; a KernelWriter.py change that alters one instruction does.

Why first. This gate is the instrument used to prove every later step safe. Every subsequent step makes structural changes to the code; without automated assembly-regression detection, correctness depends on manual inspection. Building the instrument last is not an option. Note the honest scope: this is not a pure CI-configuration change -- the byte-level golden must be built first.

Step 2. Prototype Fused Attention as a forcing function

Write a minimal Fused Attention kernel generator -- not production-quality, not wired into the main path -- that exercises the cross-loop softmax reduction. Fused Attention computes softmax((Q K^T) / sqrt(d)) V in one GPU kernel; the cross-loop softmax denominator requires knowing the row maximum before normalizing, which spans loop iterations in the GEMM and cannot be a simple post-multiply step. The prototype must produce assembly on at least one target architecture (gfx90a or gfx942).

Done condition. A script -- not a full PR, not production code -- runs end-to-end: takes an Attention problem description, emits assembly via the prototype, and the assembly assembles without errors. Single kernel, single architecture is sufficient.

Why second. The composable model's biggest unproven claim is that Attention's cross-loop reduction fits the composed structure. If the prototype shows the reduction is not separable in the way the model requires, that discovery costs a throwaway script, not a registry and a boundary refactor built on a broken assumption.

Step 3. Introduce the CodegenRequest projection (byte-identical proof)

Add CodegenRequest as a typed Python dataclass. Add GemmLoweringBackend as a class wrapping the existing kernelBody chain without changing it. Wire a parallel call path in the characterization harness and assert byte-identical output from both paths for every kernel in the gfx90a and gfx942 attribution JSONs. [Verified: feat-jit/brief.md, section 3, Step 1]

Done condition. test_request_boundary_gemm_parity.py passes: both paths produce character-for-character identical assembly for all 98 kernels. The CI gate from step 1 still passes.

Why third. Steps 1 and 2 have proven the gate works and that Attention is structurally possible. This step adds the new boundary without moving any seam -- the old path still runs, the new path runs in parallel. Divergence triggers an immediate test failure. No seam is moved yet.

Step 4. Open the registry

Add the _BACKENDS dictionary and the register_backend function. Register GemmLoweringBackend at import time. Add a stub AttentionLoweringBackend that raises NotImplementedError but registers as "ATTENTION". Verify that problem["OperationType"] = "ATTENTION" no longer raises at Problem.py:948. Verify that GEMM goldens are unchanged.

Done condition. AC-3 from feat-jit/brief.md passes: git diff HEAD -- Tensile/SolutionStructs/Problem.py shows zero changes to any OperationType == "GEMM" branch. The 98 GEMM goldens are byte-identical. The stub test passes. [Verified: feat-jit/brief.md, section 4, AC-3]

Why fourth. The CodegenRequest boundary is proven byte-identical. Opening the registry is now a safe addition: it does not touch the GEMM path. Opening the registry before step 3 would leave no machine-enforced proof that the dispatch layer does not alter GEMM output.

Step 5. Build the composable model (GEMM degenerate case, byte-identical)

Implement the composable kernel model for the GEMM degenerate case: a single GEMM expressed as a degenerate composed operation. AC-4: AttentionLoweringBackend.emit with sequence_length=1, no mask, and identity softmax must produce byte-identical assembly to GemmLoweringBackend.emit for equivalent GEMM dimensions. [Verified: feat-jit/brief.md, section 4, AC-4]

Done condition. AC-4 passes. The 98 GEMM goldens are still byte-identical. No new test failures.

Why fifth. This step empirically retires the composable model's core risk. The controlled environment now exists: gate (step 1), structural proof of Attention (step 2), byte-identical boundary (step 3), open registry (step 4). A failure here is a small, isolated test failure -- not a broken production path. A pass means the highest-risk claim in the project is verified.

Step 6. MoE strategy and Attention (real implementation)

Promote MoE from an inline GEMM flag -- checked at four sites in KernelWriter.py (lines 4739, 4787, 5878, 5914) via kernel["ExpertSchedulingMode"] > 0 [Verified: feat-jit/brief.md, section 1.4] -- to an explicit field on the CodegenRequest. Implement the real AttentionLoweringBackend using the composable model proven in step 5.

Done condition. The Attention prototype from step 2 is replaced by a production AttentionLoweringBackend. The MoE field is explicit on the request. The GEMM goldens are still byte-identical. Attention has its own golden suite (at minimum one kernel, one architecture).

Why sixth. Every unproven risk is retired. Implementing real features before step 5 means building the Attention backend on a composable model that has not been proven byte-identical -- the exact risk the ordering is designed to avoid.

Step 7. JIT serialization round-trip

Wire the serialization round-trip: a CodegenRequest serialized to JSON, shipped to a worker process, deserialized, and re-emitted must produce byte-identical assembly. This is AC-6. [Verified: feat-jit/brief.md, section 4, AC-6]

Done condition. AC-6 passes: a CodegenRequest round-trips through JSON serialization and produces byte-identical output on re-emit in a process that has never imported globalParameters.

Why last. JIT requires everything else first: serializable boundary (step 3), open registry (step 4), byte-identical composable model (step 5), real backends (step 6). Attempting JIT before the boundary is proven byte-identical produces a system that works sometimes and fails silently when process-global state differs between caller and worker. Step 1 built the instrument that catches that failure; step 7 is when it runs the final proof.

Design rationale.

  • intent: StoreState is a 1131-LOC stateful object with 516 self-accesses and no tests; it computes store-element geometry, allocates VGPR/SGPR resources, and manages a VGPR-pool lifecycle in one class. The first cut separates the pure geometry computation from the stateful resource management so each can be tested and evolved independently.
  • pattern: references/extract-computation + gof-value-object (reshaped)
  • gains -- testable: StoreElementGeometry.compute is a pure function of (kernel, batchElements) returning a value object -- unit-testable with no vgprPool or kernelWriter mock; maintainable: removes coordinate state (elementCoord0/1/sumIdx) from the 40-attribute god-object; the geometry logic stops sharing mutable self with the resource-allocation path; extensible: a pure geometry unit is where new matrix-instruction layouts (e.g. attention/MoE tile shapes) plug in without touching VGPR allocation
  • grounded at: AsmStoreState.py:408-486 [Verified]
Bottom line: the absence of tests blocks starting implementation, not authoring a plan -- the current surface, target surface, shim, and removal gates for t2-asmstorestate are all specified; step 0 is writing the goldens.
